## 一、依据与结论

- **需求是既定的**：`wiki/Menote-设计文档-v7.4.md` §7.1 已把「即时渲染」列为四档编辑模式之一（默认仍是双栏），并明确"该模式是**纯展示层**，不改变'整篇 md'的编辑粒度"。
- **技术路线也是既定的**：`wiki/Menote-项目架构-v1.md` §3.3 写明"基于 Lezer 语法树的装饰（`Decoration.replace` / `widget`），**只对视口内的节点计算装饰**"（该句原文的"光标所在行显示源码"已由 v7 / 架构 v1.25 改为"光标进入被隐藏标记时才显现该节点源码"）。
- **本轮结论**：**可行且已落地**。全部所需能力都来自已有的 CodeMirror 6 包，**没有新增任何生产依赖**。
- **一个必须知道的前置事实**：`@codemirror/lang-markdown` 的 `markdown()` **默认 base 是纯 CommonMark**（不含 GFM）——在换 base 之前，编辑器语法树里 `| a | b |` 不是表格、`- [ ]` 不是任务清单、`~~x~~` 不是删除线（`[x]` 甚至被解析成链接）。现在统一改用 `markdown({ base: markdownLanguage })`（`markdownLanguage` = commonmark + GFM + 下标/上标/emoji，由该包自己导出，不引新依赖）。

## 三、交互细则

1. **语法完整就立即渲染**（v7 定，取代「按行显示源码」）：光标是否在那一行、是否停在已格式化的文字内部，都不影响呈现——完整识别到的语法立即按样式显示。
   - **失焦整篇渲染**（v3 起保留）：CM6 的选区在打开文档时默认落在文档开头，若按"光标所在行"执行，刚打开一篇笔记会看到第一行一直露着 `##`——像"没渲染"。失焦即整篇渲染。
2. **光标进入被隐藏的标记才显现源码**（v7 定，取代「跨行选区整段露源码」）：折叠光标落进某个被隐藏标记的半开区间 `[from, to)` 时，临时显现**包含该标记的最小受支持语法节点**的完整源码（例：命中链接任一 `[]()` 或地址字符 → 显现整个链接节点；嵌套语法的**最内层**优先）；离开该区间立即恢复渲染态。**非折叠选区不因跨过标记而揭示**，继续保持渲染样式，但复制到纯文本剪贴板的 `text/plain` 仍取底层 Markdown，标记不得从结果丢失。
3. **藏掉的标记不再是原子区间**（v7 定，取代「原子区间一次跨过去」）：`EditorView.atomicRanges` 已取消——否则第 2 条永远不可达（原子区间让鼠标与方向键都进不去该位置）。方向键、鼠标点击、退格/删除现在都可以落在标记字符上，显现与否由第 2 条决定。这条同时是"用户能直接编辑被隐藏的标记"的前提。
4. **点击已渲染文本**：由 CM6 自己映射光标位置（占位块 `ignoreEvent() = false`，不吞掉鼠标事件）。
5. **中文输入法**：`view.composing` 期间**不重算装饰**，只把已有装饰按变更映射（`RangeSet.map`）——重算会把组合中的字/候选区替换掉。见 §四-2。
6. **表格条目不显示模式切换**（既有口径）：表格有自己的"表格 / 图册"档位，即时渲染对它没有意义。

## 四、实现约束与性能

1. **只算视口**：Lezer 的树是**懒解析**的（实测：建 `EditorState` 后树只覆盖前 ~3011 字符），所以插件里用 `ensureSyntaxTree(state, 视口末端, 50ms)` 补可见区；超预算就退回部分树——那一屏先显示源码，下一帧再渲染。装饰构建本身很便宜（实测视口 4KB 约 0.4–1.1ms / 397 处）。
2. **输入法安全**（本项目最该守的一条，中文优先）：组合期间跳过重算 + 位置映射；这条**只能靠人工用真实输入法验**，见 §七-1。
3. **重建时机**【2026-10-01 改】：原先是 `docChanged | viewportChanged | selectionSet | focusChanged` **任一**成立就同步重算一遍（含 `ensureSyntaxTree` 的补解析），等于**敲一个字、按一次方向键各付一次**。现在分开处理：

   | 触发 | 策略 | 理由 |
   |---|---|---|
   | `docChanged` | 停手 **90ms** 后重算 | 连续打字期间一次都不补解析语法树。位置已由 `map(changes)` 保住，装饰不会指向已消失的区间 |
   | `selectionSet` / `focusChanged` | **下一帧**重算（同帧多次合并成一次） | 光标进/出被隐藏标记要跟手；一帧内多次更新只算一次 |
   | `viewportChanged` | 下一帧重算 | 滚进新区域要有装饰，延迟一帧不可见 |
   | **`syntaxTree(state)` 引用变了**【v7 新增】 | 下一帧重算 | 后台解析推进（ParseWorker 取到新树后自己 `view.dispatch({effects: Language.setState})`）与语言树被取树这两条路径**只改树、不改文档**，原实现完全不认；不补这一条，慢解析的长文档会一直停在旧装饰上。**基准必须取「state 当前的树引用」，不能取「上次 build 用的树」**，否则本插件自己的 `ensureSyntaxTree` 会造成逐帧重建 |
   | **「正在编辑的那一行」冻结**【v8 新增】 | 上述任一路径触发重算时，**光标所在行**改用手上锁定的那一份装饰，其余行照常重算；`{L, R}` 变化或改动含跨行变更即解锁 | 光标停在某一行期间该行反复被重装饰，会让「新敲进去的标记立刻被藏起来 + 该行字号/行高跳变」，用户看到的是「写不出 `##` 标题 + 闪动」。**判据不动、只改时机**：冻结的正是"这一行渲染迟一步"这一代价。解锁条件必须与"显现结论变化"绑定，否则方向键进标记就显现不出来；**冻结只吃 point 装饰**（`Decoration.replace` / `Decoration.line`），代码高亮 token 是 `Decoration.mark`，永远跟着内容走 |

   参考外部项目 inkstone 的 `live-preview.ts`（同为 CM6 + 自写 live preview，它那边是块级缓存 + 90ms 防抖）。差别是我们装饰的是**语法节点**而非渲染好的 HTML，没有"复用未变块的 HTML"那一层，只做时机上的合并。`destroy()` 撤掉两个定时器。
4. **可测性**：核心是**纯函数** `buildLivePreviewDecorations(input: LivePreviewInput) → { decorations, reveal }`——只依赖 `EditorState` 与语法树（`reveal` 是该行/该位置的显现区间结论，§2.2 的冻结判据就比对它），不需要视图，所以能在 jsdom 里逐条断言（全仓既有的 CM6 测试都只能 mock 掉整个编辑器）。**节流与冻结只发生在插件层，纯函数的签名与行为一字未改**，原 19 条用例原样全绿（v8 起另有 `live-preview-lock.test.ts` 钉子用例）。
5. **切换不重建文档**：`live` 走 `Compartment` 重配置（与只读开关同一套），"仅编辑 ↔ 即时渲染"在 React 树里位置相同、不会重新挂载；行号与即时渲染扩展互斥（渲染视图里行号只是噪声）。

## 六、实测（2026-09-28，本地真实 Chrome + 同一套量法）

| 项 | 结果 |

## 八、有意与 Obsidian / Typora 不同的地方

| 点 | 我们的做法 | 理由 |
|---|---|---|
| 表格 | 保持源码 | 表格就地编辑是子项目级工作量；表格条目另有专门界面 |
| 代码块 | 围栏保留 + 底色 | 藏围栏会在块头留一个空行（CM6 折叠整行的写法很啰嗦），收益不抵复杂度 |
| 任务清单 | 保持源码 | 不放假复选框（`DESIGN.md` 禁止"点了没反应的控件"）；真交互留下一步 |
| 图片 | 占位块 | 用户 2026-09-28 拍板的首期范围 |
| 失焦时 | 整篇渲染 | 见 §三-1（否则刚打开笔记像"没渲染"） |
