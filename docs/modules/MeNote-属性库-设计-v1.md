## 1. 起因

用户 2026-10-11 报出一篇外部导入笔记的属性异常：[实测确认] 该篇 front matter 里的 `status: "unread"` 在属性卡片里**看不到值**，卡片上只有一行

> `status: unread` 不是 MeNote 认识的值，改动上面这几行会把它覆盖掉。

同一篇里的 `url` / `author`（块序列）/ `captured` / `like` 都正常显示，只有它被"吃掉"了。用户据此提出：

> 是否可以在编辑器里加一个属性设置，专门编辑配置属性值，出现未识别的可以提示是否要添加到属性库中，这样会不会更方便

用户先选定方向「先写设计稿，按「键值字典」做」（本稿 v1），随后（2026-10-11，第二轮）把模型说全，本稿 v2 按这套口径改写：

> 库是公共的，相当于是一个 yaml 编辑器，可以在文档编辑时在前台添加，也可以在设置里管理添加，也能通过导入文档时对陌生属性录入式添加。但是删除某种属性只能在管理页面处理，前端编辑时只能选择用或者不用。design 可以改动

## 2. 现状（v0.8.29 已实现的口径）

**卡片**（`apps/web/src/features/notes/ui/ItemProps.tsx`）在正文区顶部、标题带之下，固定四行自有属性 + 一段「其他属性」：

| 位置 | 行为 | 代码 |
| --- | --- | --- |
| 标签 | 只读 front matter 的 `tags`（**不并正文 `#标签`**），chip + × | `readItemProps` `ItemProps.tsx:91-114` |
| 状态 / 截止 / 优先级 | 三项都回落空值；状态无「未设为清单」项（2026-10-11 决定） | `ItemProps.tsx:272-389` |
| 其他属性 | 顶层其余键**原样**列出，值按原格式（块序列给多行框） | `readForeignKeys` `packages/mdcore/src/frontmatter.ts:407` |
| 新增属性 | `window.prompt` 键名 → 空值 | `ItemProps.tsx:222-239` |
| 删除属性 | ⓧ + 二次确认（说的是"删完 md 里就没有了"） | `ItemProps.tsx:468-483` |
| 未识别值 | **只有一处**：被清单接管的三个键里"原文有值、归一后为空"的那些，一行文案 | `unrecognizedTaskValues` `ItemProps.tsx:125-141` |

**清单接管是无条件的**：YAML 里有没有 `status` / `due` / `priority` 这三个顶层键，就决定这篇是不是清单条目（`deriveTaskFields` `packages/mdcore/src/tasks.ts:126`），而它们的值是**封闭枚举**（`TASK_STATUS_LABELS` / `TASK_PRIORITY_LABELS`，`packages/mdcore/src/tasks.ts:24-34`）。所以 `status: unread` 的"消失"不是解析失败——[实测确认] mdcore 把这篇解析得好好的（`title` / `tags` / `task` / 四个外来键都在），是**清零后没有位置显示**。

**导入**：`apps/web/src/features/notes/ui/ImportNotesFlow.tsx`（隐藏文件选择器 → 多选确认 → 结果），由 `NbAddButton.tsx:32` 的 `+` 菜单唤起；解析与入库在 `apps/web/src/features/notes/import-md.ts`，正文原样保留。

## 3. 属性库是什么

### 3.1 一句话

**属性库 = 一份账号级、全站唯一一份的属性定义表**：每个条目是一个键（可选带类型与候选取值）。它有三张脸：

- **取用面**（前台）：正文区顶部的属性卡片——从库里挑键来用、给值；
- **管理面**（设置）：设置 › 属性库——增、改、删条目（**唯一能删的地方**）；
- **入口面**（导入）：导入文档时把库里还没有的键逐个"录入式"补进库。

因此它确实如用户所说，是**一台 YAML 属性编辑器**——只不过编辑的是"属性本身"（有哪些键、键是什么类型、用过哪些值），不是某一篇的 front matter。

### 3.2 条目存什么（草案）

```ts
export const PropLibraryEntrySchema = v.object({
  /** 键名。原样使用，不汉化、不显示别名（§3.4） */
  key: v.string(),
  /** 内置键为 true：title / tags / status / due / priority，不可删、不可改键名 */
  builtin: v.optional(v.boolean(), false),
  /** 类型只影响前台控件，不参与 md 解析与往返 */
  type: v.optional(
    v.union([
      v.literal("text"),    // 单行
      v.literal("multiline"), // 块序列（YAML 列表）/ 多行文本
      v.literal("date"),    // 日期
      v.literal("number"),
      v.literal("boolean"),
      v.literal("choice"),  // 枚举，取值由 values 定
    ]),
    "text",
  ),
  /** 用过的取值（最近用的在前）。与 type=choice 的差别见下 */
  values: v.optional(v.array(v.string()), []),
});
```

- **文本类**（`text` / `multiline` / `date` / `number`）：`values` **只是候选**，不校验——库里没有的值照样写得进去（否则导入的笔记会被"字典"判成非法）。
- **`choice`**：`values` 就是取值范围，前台给下拉而不是输入框。**只有用户明确把某个键设成 `choice`** 才会收窄，默认不收窄。
- 内置键的 `values` 另有一套规则（清单三键），见 §5。

### 3.3 「用 / 不用」与「删条目」是两件事

| 动作 | 在哪 | 影响面 |
| --- | --- | --- |
| **用** | 前台卡片：从库里选一个键 → 写进本篇 front matter | 这一篇 |
| **不用** | 前台卡片：把该键从本篇 md 里移除（库里条目留着） | 这一篇 |
| **登记值** | 前台卡片：给某个键填了新的值 → 该值进库做候选 | 全部文档的候选 |
| **改条目** | 设置 › 属性库：改类型、增删候选值、改键名（键名改动只影响库，**不回写任何文档**） | 库 |
| **删条目** | 设置 › 属性库：**只有这里能删** | 库（文档里的键变成"未入库的键"，md 不动） |

这一条是用户口径的直接落地：**前台永远不动库结构**（只决定"这篇用不用"），**库结构的增删改只发生在设置页**。好处是破坏性操作只有一个入口、影响面可以在一句话里说清；代价是前台删一个属性之后它还留在候选里（这是**有意**的：那正是"不用"而不是"删掉"）。

### 3.4 硬边界（不变）

- ❌ **库不参与 md 解析**。`mdcore` 不读库：不认识的值仍按原格式原样往返（「键名原样、值不替用户猜」的底线，`ItemProps.tsx:7-13`）；
- ❌ **不做键名的中文化 / 显示名**。`url` 就叫 `url`——贴上「来源链接」等于替用户猜它是什么意思，猜错比不猜更糟；
- ❌ **不自动往库里塞东西**（见 §6.4）；
- ❌ **库不定义清单语义**。内置三键的语义（什么算完成、归哪一列、怎么统计）仍在清单功能里；库若接纳它们的额外取值，必须同时给出归一关系（§5）。

## 4. 存储：账号级（定案）

用户口径「库是公共的」+「在设置里管理添加」= **跟随账号**，跨设备、跨笔记本、跨条目共用一份。

- `user_settings` 是**整份 JSON** + `GET/PUT /api/settings`（`apps/worker/src/routes/settings.ts:31` / `:35`）+ **已参与同步**（`apps/worker/src/services/sync.ts:200` 随下拉一起下发）+ 本机有 IndexedDB 缓存与 outbox（`apps/web/src/data/db/settings.ts`）。
- 加字段的既有纪律是 `v.optional(…, 默认值)`（`packages/shared/src/settings.ts:310/319/324/329/334/339` 六处都这么加）：**老行、旧客户端 PUT 不带该字段都不会被 422，服务端读旧 JSON 由 schema 补默认值——不需要迁移**。
- 要动 `packages/shared/src/settings.ts` 的公共类型与 API 契约（同一个接口加一个可选字段，向后兼容）→ 属 `AGENTS.md`「先确认再动」区，需你点头。
- **本机 `localStorage` 方案已弃**：与"公共"直接冲突（换设备就没有了），也会成为第二个「本机」例外、按 v0.8.16 收窄后的口径还得打标。

**已知缺口**（与本设计有关，单独定）：备份契约里有 `settings.json`（`packages/shared/src/backup.ts:32` 的 `SETTINGS_NAME`），但**这个常量当前没有任何引用**——`apps/web/src/features/backup/export.ts:146-154` 只写了 `folders.json` 等，不写设置。也就是说账号级的属性库**目前不会进备份**。

## 5. 关键决策：内置键上的陌生值

用户原话是"未识别的可以提示是否要添加到属性库中"。**先把性质说清**：库能治的是"这个键我不认识"，治不了"这个值是我不认识"——后者发生在**内置键**上。

- 内置键的语义在清单功能里：`status` 的值决定这篇算不算完成、在清单视图归哪一列、统计怎么算（`packages/mdcore/src/tasks.ts:24-34`）。
- 若只在库里登记 `unread` 就"不再提示"，用户会以为它被接纳了，而清单侧仍不认它、行上仍不显示——**提示静音了，语义没变，是自欺**。

所以有两条路，**必须选一条**：

**路 A（本稿默认）：只做「可见 / 可改 / 可留」，不动值域。**

卡片上那一行从"警告"升级为"一条能操作的属性"：

- 显示**原值本身**（`status: unread`），不只是"改上面会覆盖"的警告；
- 两个动作：① **改成 MeNote 认识的值**（状态三档 / 清空）；② **保持原样**——不动它、继续原样显示、继续不参与清单。

**路 B：内置键的值域扩展（需要归一档）。**

在管理页给 `status` 加取值时，**必须同时指定它归到哪一档**（`unread → todo`）：这样清单视图、统计、`items` 派生列全都照旧（存的仍是 `todo`），而卡片上显示原值 `unread`、下拉里也有它。代价与要查的东西：`items.status` 的取值是否有 CHECK 约束、服务端与同步侧对三档是否有枚举校验、`deriveTaskFields` 的归一表怎么放——**这些要在动工前查实并写进实施计划**。

> 路 B 才是"属性库接管一切"的完整形态，但它实质是清单功能的值域扩展 + 属性库，建议**分开做**：先上路 A（本稿），路 B 另开一稿。

## 6. 界面稿（先稿后码）

### 6.1 前台卡片：从「增删」改成「用 / 不用」

- **固定四行**（标签 / 状态 / 截止 / 优先级）不变——它们是内置键的专用控件；
- **「其他属性」段常显**（库里一个键都没用过也显示），标题右侧是「**+ 用一个属性**」：
  - 空库：只有一项「新建键…」；
  - 有库：已知键列表（最近用的在前，标出类型）+ 末尾「新建键…」；
  - 选定键后：按类型给控件（文本 / 多行 / 日期 / 数字 / 布尔 / 下拉），文本类另给该键已有取值的候选（`datalist`）；
- 每个已用属性的 ⓧ 语义改为「**本篇不用**」，二次确认文案相应改成"这一篇不再有这个属性（库里的定义还在）"；
- 未入库的键（导入带进来的）在行尾标一个「未入库」+ 一键入库；
- 键名规则与保留键判定不变：`KEY_PATTERN`（`ItemProps.tsx:86`）、`RESERVED`（`:88`，含 `title` / `tags` / `menote` / `status` / `due` / `priority`）。

### 6.2 设置 › 属性库（管理页）

- 内容：条目列表（键名 + 类型 + 候选取值 + "被 N 篇用到"）+ 新建 / 改类型 / 增删候选值 / 改键名 / **删除条目**；
- 删除条目必须**二次确认**，且写明后果："库里删掉后，已经用了它的笔记里的键还在（md 不动），但会变成'未入库的键'、不再出现在候选里"；
- 内置键（`title` / `tags` / `status` / `due` / `priority`）在列表里标「内置」，不可删、不可改键名；
- **挂在哪个分类**：推荐**新增第 10 个分类「属性库」**（它有真实内容：增删改查 + 内置键说明）。备选是并进「通用」当一张卡。注意 v0.8.4 的教训（11 类收到 9 类，理由是粒度严重不均）——若担心导航再次变长，就走备选。
- 走新增分类时：`apps/web/src/app/router.ts:29-43` 的 `SETTINGS_PAGES` 加一项；新 id 不需要 `LEGACY_SETTINGS_PAGES` 映射（那是撤销分类时才要的，`:51-54`）。

### 6.3 导入时的录入步

在 `ImportNotesFlow.tsx` 的结果之前插一步（**只在真扫出陌生键时出现**，否则不打断）：

- 列出本次导入的文件里**库里没有的键**（去重）+ 每键出现几篇 + 抽一个样例值；
- 每行两个动作：**录入**（选类型，可选"记住这些取值"）/ **跳过**；
- 默认动作是**跳过**（不选就当没看见，不往库里塞东西——与 §6.4 同一条原则）；
- 跳过不影响导入结果：键照旧在卡片里以"未入库"显示，随时可以再录。

### 6.4 学进库的时机

**只在用户主动动过时记**（新建键、改过某个键的值、导入时点了"录入"）。卡片渲染**不自动收录**——否则浏览一遍导入的几十篇笔记，就会把一次性垃圾键全收进候选里。这一条可以按实际使用体验再调（最简原则）。
