## 1. 起因

用户 2026-10-11 报出一篇外部导入笔记的属性异常：[实测确认] 该篇 front matter 里的 `status: "unread"` 在属性卡片里**看不到值**，卡片上只有一行

> `status: unread` 不是 MeNote 认识的值，改动上面这几行会把它覆盖掉。

同一篇里的 `url` / `author`（块序列）/ `captured` / `like` 都正常显示，只有它被"吃掉"了。用户据此提出：

> 是否可以在编辑器里加一个属性设置，专门编辑配置属性值，出现未识别的可以提示是否要添加到属性库中，这样会不会更方便

用户随后选定方向：**先写设计稿，按「键值字典」做**。本稿就是那份设计稿。

## 2. 现状（v0.8.28 已实现的口径）

**卡片**（`apps/web/src/features/notes/ui/ItemProps.tsx`）在正文区顶部、标题带之下，固定四行自有属性 + 一段「其他属性」：

| 位置 | 行为 | 代码 |
| --- | --- | --- |
| 标签 | 只读 front matter 的 `tags`（**不并正文 `#标签`**），chip + × | `readItemProps` `ItemProps.tsx:91-114` |
| 状态 / 截止 / 优先级 | 三项都回落空值；状态无「未设为清单」项（2026-10-11 决定） | `ItemProps.tsx:272-389` |
| 其他属性 | 顶层其余键**原样**列出，值按原格式（块序列给多行框） | `readForeignKeys` `packages/mdcore/src/frontmatter.ts:407` |
| 新增属性 | `window.prompt` 键名 → 空值 | `ItemProps.tsx:222-239` |
| 删除属性 | ⓧ + 二次确认 | `ItemProps.tsx:468-483` |
| 未识别值 | **只有一处**：被清单接管的三个键里"原文有值、归一后为空"的那些，一行文案 | `unrecognizedTaskValues` `ItemProps.tsx:125-141` |

**清单接管是无条件的**：YAML 里有没有 `status` / `due` / `priority` 这三个顶层键，就决定这篇是不是清单条目（`deriveTaskFields` `packages/mdcore/src/tasks.ts:126`），而它们的值是**封闭枚举**（`TASK_STATUS_LABELS` / `TASK_PRIORITY_LABELS`，`packages/mdcore/src/tasks.ts:24-34`）。所以 `status: unread` 的"消失"不是解析失败——[实测确认] mdcore 把这篇解析得好好的（`title` / `tags` / `task` / 四个外来键都在），是**清零后没有位置显示**。

## 3. 属性库是什么（硬边界）

**属性库 = 用户自己维护的「键 → 已知取值」表**，只服务两件事：

1. 新增属性时**给候选**（已知键名列表；选定键后给该键用过的取值）；
2. 让外来键的取值**跨笔记复用**，不必每次重打。

它**不是**：

- ❌ **不参与 md 解析**。`mdcore` 不读属性库：不认识的值仍按原格式原样往返（这是「键名原样、值不替用户猜」的底线，`ItemProps.tsx:7-13`）；
- ❌ **不改清单三字段的语义**（理由见 §5）；
- ❌ **不做键名的中文化 / 显示名**。`url` 就叫 `url`——贴上「来源链接」等于替用户猜它是什么意思，猜错比不猜更糟；
- ❌ **不自动往库里塞东西**（见 §6.4）。

## 4. 数据形状与存储

### 4.1 形状（草案）

```ts
export const NotePropsSettingsSchema = v.object({
  /** 键名 → 见过的取值。顺序即候选顺序（最近用的在前） */
  keys: v.optional(
    v.array(
      v.object({
        key: v.string(),
        values: v.optional(v.array(v.string()), []),
      }),
    ),
    [],
  ),
});
```

`values` **只用于提示**，不用于校验：库里没有的值照样能写进去（否则导入的笔记会被"字典"判成非法）。

### 4.2 存哪：两个方案

**方案 A（推荐）：账号级，放进 `user_settings`**

- 现成通道全都在：`user_settings` 是**整份 JSON** + `GET/PUT /api/settings`（`apps/worker/src/routes/settings.ts:31` / `:35`）+ **已参与同步**（`apps/worker/src/services/sync.ts:200` 随下拉一起下发）+ 本机有 IndexedDB 缓存与 outbox（`apps/web/src/data/db/settings.ts`）。
- 加字段的既有纪律是 `v.optional(…, 默认值)`（`packages/shared/src/settings.ts:310/319/324/329/334/339` 六处都这么加）：**老行、旧客户端 PUT 不带该字段都不会被 422，服务端读旧 JSON 由 schema 补默认值——不需要迁移**。
- 属性库是"我知道 `captured` 是什么"这类个人知识，换设备后重新积累很痛——正是「跟随账号」的典型。
- **代价与边界**：要动 `packages/shared/src/settings.ts` 公共类型与 API 契约（同一个接口加一个可选字段，向后兼容）→ 属 `AGENTS.md`「先确认再动」区，需你点头。
- **已知缺口**（与本设计有关，需单独定）：备份契约里有 `settings.json`（`packages/shared/src/backup.ts:32` 的 `SETTINGS_NAME`），但**这个常量当前没有任何引用**——`apps/web/src/features/backup/export.ts:146-154` 只写了 `folders.json` 等，不写设置。也就是说走方案 A 的属性库**目前不会进备份**。要不要顺手补 `settings.json`，是另一个决定（可另开一条）。

**方案 B：本机 `localStorage`**

- 照抄 `apps/web/src/features/notes/props-collapse.ts:16-36` 的写法（`menote:notes:prop-library`），零后端、零契约改动；
- 代价：它会成为第二个「本机」例外。按 v0.8.16 收窄后的口径（**只标"本机"= 只在这台设备生效**），设置页上必须给它打「本机」标，而那正是刚收窄掉的东西。

## 5. 关键决策：自有键上的陌生值，救不救？

用户的原话是「出现未识别的可以提示是否要添加到属性库中」。**对 `status: unread` 这一例，这条路走不通**，理由必须写清楚：

- 清单状态是封闭枚举（`packages/mdcore/src/tasks.ts:24-34`）。让它多一档 `unread`，连带要定的是：它算不算完成？清单视图归到哪一列？统计怎么算？`items` 的派生列怎么存？——那是**清单功能的值域扩展**，不是属性库能顺手带出来的东西。
- 若只做到"加进库就不再提示"，用户会以为 `unread` 已被接纳，而清单侧仍然不认它、行上仍然不显示它的值——**提示静音了，语义没变，是自欺**。

所以本设计把"未识别"分成两类，区别对待：

| 类别 | 例子 | 属性库能做什么 | 卡片该怎么办 |
| --- | --- | --- | --- |
| **外来键** | `url` / `author` / `captured` / `like` | 记键名与取值，做输入候选 | 本来就原样显示，无需改 |
| **自有键上的陌生值** | `status: unread` / `priority: p1` | **不管**（值域由 MeNote 定义） | 把那一行警告升级为「可见、可改、可留」的一行 |

**自有键陌生值那一行的形态（草案）**：

- 显示**原值本身**（`status: unread`），不只是"改上面会覆盖"的警告；
- 两个动作：① **改成 MeNote 认识的值**（状态三值 / 清空；优先级同上）；② **保持原样**——不动它、继续原样显示。**"能不能留住原值"由它回答**；
- 清空 = 删掉那个键（走现有 `replaceFrontmatter` 路径）。

> 若你要的其实是「状态能有 `unread` 这一档」，那是清单功能的值域扩展，另开设计；本稿把它列进 §8「不在范围」。

## 6. 界面稿（先稿后码）

改动只落在属性卡片上：**不新增页面、不新增设置分类**（设置页刚从 11 类收到 9 类，粒度不均的坑不该再踩一次）。

### 6.1 「+ 添加属性」改成锚定菜单

现在是 `window.prompt("键名（只能用字母、数字、下划线、连字符）")`（`ItemProps.tsx:223`）——给不了候选、看不见已有的键、移动端也不好用。改为复用 `DropdownMenu`（`apps/web/src/app/ui/Menu.tsx`，`blocks` 用来放"不是单个菜单项"的内容）：

- **空状态**（库里一个键都没有）：菜单里只有一项「新建键…」；
- **有键**：已知键列表（最近用的在前）+ 末尾「新建键…」；
- 选定键后：值输入框 + 该键已用取值的候选（`datalist`），值仍可自由输入；
- 键名规则与保留键判定**不变**：`KEY_PATTERN`（`ItemProps.tsx:86`）、`RESERVED`（`:88`，含 `title` / `tags` / `menote` / `status` / `due` / `priority`）。

### 6.2 未识别值那行

`ItemProps.tsx:397-401` 的 `itemprops__warn` 升级为「原值 + 拾取器 + 保持原样」。文案仍**保持可见**（`AGENTS.md`：错误 / 校验必须可见，说明性文字才收进 `InfoHint`）。

### 6.3 属性库的管理

**不做独立管理页**。"忘掉某个键 / 某个取值"就地放在候选列表项的 ⓧ 上——它只改本机字典、不碰 md，**不需要二次确认**（与删属性不同，那个要确认，见 `ItemProps.tsx:447`）。

### 6.4 学进库的时机

**只在用户主动动过时记**（新建键、改过某个键的值）。卡片渲染**不自动收录**——否则浏览一遍导入的几十篇笔记，就会把一次性垃圾键全收进候选里。这一条可以按实际使用体验再调（最简原则）。
