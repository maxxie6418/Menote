## 一、目标与范围

### 1.1 目标

本稿讨论两项相互关联、但应分别验收的体验问题：

1. **编辑器首次可用等待**：用户打开应用并进入空闲状态后，在后台预载编辑器代码；用户首次切入正文编辑或即时渲染时，不应再等待组件代码首次下载和执行。
2. **即时渲染的编辑反馈**：在「即时渲染」模式下，已完整识别的 Markdown 语法应在继续留在当前行、甚至光标停留在已格式化文字内部时呈现样式；用户不必把光标移到另一行才能看到效果。

本稿以「Typora 式连续写作感」描述体验方向，不把与 Typora 功能或视觉完全对齐作为通过标准；通过与否以本稿明确的交互与性能验收项判定。

### 1.2 范围与非目标

- 首轮只讨论现有「即时渲染」已覆盖的 Markdown 语法：标题、粗体/斜体、删除线、行内代码、Markdown 链接、尖括号自动链接、裸 URL、引用、有序/无序列表、分隔线、图片与代码块、任务清单。**基线是 v0.8.36 的实现**：图片为内联真图（只有 `#pending` 上传中才是文字占位块）、代码块内容行有 Prism 语言高亮、任务清单有真复选框（`apps/web/src/app/editor/live-preview.ts` 与 `code-highlight.ts`）——本稿在这三处只谈「何时呈现」，不重复设计它们的能力，也不借此扩展表格、front matter、`#标签` 或其他独立功能。
- 「仅编辑」继续作为查看和编辑原始 Markdown 的明确入口；本稿不改变其语义，也不改变「仅预览」模式。
- Markdown 正文仍是唯一持久化真值；不引入富文本持久化格式、不改数据模型、同步协议、保存策略或生产依赖。
- 本稿的**门槛改动（§2 与 §4.2）与三份现行定稿冲突，按用户 2026-10-18 决定标为「待议提案」，不改定稿**：`wiki/Menote-项目架构-v1.md` §3.3、`docs/modules/Menote-即时渲染-设计-v1.md` §三、`docs/modules/Menote-编辑器专项优化-设计-v1.md` D1 都定稿了「光标所在行显示源码」，而本稿要改成按语法节点与标记范围判定。**在用户明确确认新方案、并授权同步既有定稿文件前，这三份现行规则继续有效；本稿不自动覆盖它们。**其余部分（§3 预载、§4.3 解析续刷、§5 验收）不与现行定稿冲突，可独立成立。
- 本阶段只编写并评审设计，不实现代码、不修改 wiki 或现有设计文档。

## 二、交互契约

> **本节（§2）与 §4.2 属待议提案。** 它提出将现有「光标所在行显示源码」规则改为基于语法节点的即时渲染，与三份现行定稿冲突；在本稿正式确认并获用户授权改定稿之前，仍以现行生效设计为准。

### 2.1 已完成语法立即呈现

- 在「即时渲染」模式下，一旦当前文档变化使现有解析器识别出完整语法，编辑器应在该次更新后的最早可呈现时机应用对应样式；不要求离开当前行，也不增加固定防抖等待。
- 完整语法以现有 Markdown 解析器的语法树为准：成对标记（如 `**加粗文字**`）须存在完整语法节点及闭合标记；无闭合符的块级语法（如 `# 标题`、`- 列表项`）在解析器产出对应节点时即视为完整，不能等待用户移出当前行。
- 初始方案采用「无额外防抖」。如果实际输入手感或性能测试显示需要调整，再根据证据评估最小必要的合帧或防抖；不能为了降低解析开销而默认牺牲即时反馈。
- 例如，`**加粗文字**` 被识别为完整强调语法后，即使光标仍停在「加粗文字」内部，也保持加粗呈现；`# 标题` 被解析为标题节点后，不因光标尚未离开这一行而继续显示行级 Markdown 标记；`#foo` 未被解析为标题时保持原文。

### 2.2 未完成语法保留原文

- 尚未闭合、无法识别或暂时不构成完整语法的输入保持源码原样，不做猜测式格式化。
- 例如，输入 `**加粗文字` 时仍按原文显示；用户补全闭合标记并被解析器识别后，再转为对应样式。
- 此规则只规定展示，不得改写、丢弃或规范化用户输入；底层文档始终保留原始 Markdown 字符。

### 2.3 光标、选择与源码查看

- 完整语法的呈现不依赖整行是否为活动行。折叠光标进入粗体、链接文字等已渲染内容时，不自动揭示语法标记。
- 对**折叠光标**，以底层 Markdown 的半开区间 `[from, to)` 表示每段被隐藏的语法标记；光标落入任一标记字符范围时，显现包含该标记的最小受支持语法节点完整源码（例如链接任一 `[]()` 标记或 URL 字符被命中时显现完整链接节点）。嵌套语法显现最内层匹配节点；离开标记范围后恢复渲染态。进入标记位置不能被原子区间机制悄悄跳过。
- 对**非折叠选择**，即使选区跨过一个或多个隐藏标记，也不单因范围相交而揭示源码，继续保持渲染样式；复制到纯文本剪贴板的 `text/plain` 仍取底层 Markdown，标记不得从结果丢失。折叠光标恢复后再按其位置应用标记显现规则。
- 光标移动、方向键跨越隐藏标记、选择范围与鼠标点击位置必须继续对应正确的文档偏移；装饰不能吞键、困住光标或造成跳位。
- 需要查看和直接编辑语法标记时，用户可切换到保持不变的「仅编辑」模式。

### 2.4 中文输入法与解析未完成状态

- 延续现行 IME 保护：中文输入法组合期间不重建即时渲染装饰，只映射已有装饰；不主动调用 `forceParsing` 续刷，也不派发/应用 `parseProgressEffect`。若解析进展在组合期间到达，只记录一项待刷新状态；组合结束后以最终文本建立新 generation 并更新解析/渲染一次。
- 不得因渲染而打断候选词、丢失组合文本、移动焦点或重置选区。
- 解析只处理视口及增量内容；若解析预算耗尽、当前语法树尚不完整，应在解析继续推进后主动安排装饰刷新，不能把「移开光标」变成触发下一次更新的隐式前提。

### 2.5 范围语法的逐项显示判据

`A3.15` 的**标记隐藏边界尚未实测**：v0.8.36 的 `TaskMarker` 在光标落进 `- [ ] ` 时究竟隐藏哪一段、是否随勾选状态变化，本稿不预设结论。上表只给出要问的问题与验收要求；实现阶段须先用真实编辑器跑一遍、把实测边界补进本行，再据此定死验收判据。

精确样例（输入字符串中的 `\n` 表示一个 LF；两者均无末尾 LF）：
````js
const open = "```js\nconst x = 1;";
const closed = open + "\n" + "```";
````
`open` 的 CodeMirror `doc.lines` 为 2，节点范围 `[0,18)`；`closed` 的 `doc.lines` 为 3，节点范围 `[0,22)`。范围采用半开 UTF-16 偏移（样例仅含 ASCII，故与 UTF-8 字节数相同）；底色只画节点相交的物理行，不添加 EOF 空行。

每个 A3.x 完整样例分别进行 30 次独立试验，每次重置为表中完成前状态、只执行该行测量事务，并按 §5.1 的 nearest-rank 算 p50/p95；逐项报告，不聚合掩盖单项慢点。完整样例 p95（≤100ms），并断言语法树覆盖目标后下一帧出现表中结果；未完成/未识别样例按表逐字比较 `textContent` 与源码且断言无对应装饰。裸 URL 以从 `https://example.` 追加 `i`、首次产出 `URL` 节点作为计时事务，之后再输入 `nvalid`；不把最终字符误称为识别阈值。开放围栏在 EOF 已是 `FencedCode` 节点，单独记录解析器节点与底色范围。**A3.13 与 A3.13b 分别计为两个完整样例（真图与 `#pending` 占位是两条不同分支），A3.15 的未完成态与已完成态各算一个**，因此计时样例总数为 17 条而非行数。首轮范围不得以只通过粗体和标题代替全表覆盖。

### 2.6 本节待验证点

- 无额外防抖在典型及长文档输入下是否始终保持顺畅；如果不满足，应先测出阻塞发生在解析、装饰构建还是 DOM 更新，再讨论调整，不预先写入固定等待时间。
- 隐藏语法标记时，半开偏移、嵌套语法显现、鼠标点击、方向键、非折叠跨节点选择、撤销/重做及 `text/plain` Markdown 复制是否都稳定；具体用户动作与结果已列于验收矩阵。
- 解析预算用尽后的续解析方案以 `forceParsing` 与单任务调度为候选；必须在仓库锁定的 CodeMirror 版本上证明更新、停止条件和时延，失败则先修订技术方案，不直接进入实现。

## 三、编辑器后台预载

### 3.1 触发条件

- 仅在用户已通过认证、主工作区可交互后安排预载；不在登录页下载编辑器代码。
- 工作区首屏可交互后开始调度：优先等浏览器空闲；最迟等待 2 秒后以低优先级启动，且启动前再次确认页面可见与网络策略允许，避免与应用启动的关键渲染争抢资源。
- 页面处于隐藏状态时取消尚未开始的预载调度；页面恢复可见后重新安排。已开始的浏览器模块下载不强制中断，但只共享加载结果，不得在页面不可见时强行聚焦编辑器。
- 用户主动进入编辑后，记录一次焦点意图；恢复条件与取消规则统一按 §3.3 执行。

### 3.2 调度与网络策略

- 以 `document.visibilityState === "visible"` 定义前台可见；仅在该条件成立且工作区可交互时开始计 2 秒最大等待，首屏先完成呈现。调度按能力择一：优先 `requestIdleCallback(callback, { timeout: 2000 })`；否则用 `scheduler.postTask(..., { priority: "background", signal })` 并配一个 2 秒 watchdog；两者皆不可用时只用 2 秒定时器。每次安排持有 generation 与句柄，按 API 用 `cancelIdleCallback`、`AbortController.abort()`、`clearTimeout` 取消；页面隐藏、网络策略变为跳过或用户编辑前已主动加载时，提升 generation 并取消尚未开始的回调。已启动的动态导入不强制中断。
- 所有可并发触发的预载回调（如 postTask 与 watchdog）都进入同一个同步 `claim(generation, "prefetch")`：检查 generation、认证工作区仍有效、`document.visibilityState === "visible"`、网络策略与 `state === "scheduled"`，然后先将状态同步原子改为 `claimed` 并撤销其它句柄，再启动唯一共享加载 Promise。回调触发时若条件不符则不启动；页面隐藏或网络受限导致调度被取消、但尚未发生加载失败时，恢复允许后只重新安排一次。后台加载一旦失败，不因网络/可见性变化自动重试；下一次明确的用户编辑操作按 §3.4 开始一次新的按需尝试。同一事件循环中隐藏处理与 claim 的先后以这个同步状态门为准，任何后来运行的回调都需重新检查可见性与 generation。
- 网络策略采用“任一受限信号优先”：`saveData === true` 或 `effectiveType` 为 `"slow-2g"`/`"2g"` 任一成立即跳过可选预载；只有没有受限信号时才允许。因属性缺失/未知而无法判断时默认允许；未知信号不能覆盖另一项已明确的受限信号。例如 `saveData === true` 且 `effectiveType === "4g"` 仍跳过，`saveData` 缺失且 `effectiveType === "slow-2g"` 仍跳过，二者均未知时允许。
- 2 秒是最大等待而非必须启动时间；用户主动编辑时走 `claim(generation, "user")`，绕过可选预载的省流量/空闲门槛但撤销尚未开始的预载调度，并接管同一共享加载 Promise；不重复请求。跳过预载不禁用编辑。

### 3.3 与按需加载共享任务

- 保留现有代码分割，不把编辑器静态并入首屏入口；后台预载只触发当前编辑器模块及其既有依赖。
- 后台预载和 React 懒加载渲染必须共用同一个模块加载函数与进行中的 Promise；用户在预载未完成时进入编辑，不得发起第二次相同加载。模块成功后保留已完成结果，所有并发调用共用唯一 Promise。“加载尝试数”按共享加载函数从 idle/拒绝状态转为 loading 并创建新 Promise 的次数计；并发调用加入同一 Promise 不重复计，浏览器是否实际发起 HTTP 请求、是否命中内存/磁盘缓存均不改变该次数（HTTP 请求数另作诊断）。
- 用户已主动进入编辑而模块仍在加载时，只在正文编辑区显示轻量占位；笔记内容、其它导航与应用操作不被全局遮罩或禁用。记录单调递增的焦点意图 token，并绑定 noteId 与编辑上下文 generation；模块就绪时仅在 token 仍有效、同一笔记仍处于编辑模式、页面可见且用户未主动移焦时把焦点交给编辑器。意图建立后，焦点进入编辑器以外控件、用户在外部控件上操作、离开笔记/编辑模式或页面隐藏都会取消 token；回到同一笔记必须由新的明确编辑操作建立新 token。后台预载及普通阅读/笔记切换不得抢焦点。该行为须满足第一次进入编辑的用户动作完成后即可键入，不需第二次点击；无需等模块时不得延后焦点。

### 3.4 失败回退

- 后台预载失败不能影响阅读、登录状态或其它功能，也不弹打扰提示；不因网络/可见性恢复而自动重试预载，不自动无限重试。
- 后台加载失败后，若用户尚未进入编辑，静默记录失败并清除已拒绝的共享 Promise。用户之后第一次明确进入编辑时，立即以该用户动作为触发发起且仅发起一次新的按需加载尝试；这是按需加载，不是后台自动重试。成功时直接进入可编辑状态，不先显示错误，也不要求用户再点一次。若预载失败时用户已在等待编辑，则这次共享 Promise 的拒绝视为主动加载失败。
- 按需加载尝试失败后，或用户已在预载进行期间进入编辑而共享请求随后失败，显示可理解的正文区错误状态和明确的手动重试入口；错误恢复不得丢失笔记正文。后台错误必须被妥善接收，不能产生未处理 Promise rejection。
- 用户点击“重试”时清除被拒绝的共享 Promise，并重置 React 懒加载错误边界/组件实例，使下一次调用创建唯一的新加载尝试；同一时刻不能并发出多个重试。若用户仍在该笔记编辑上下文中，重试成功后清除错误并恢复焦点；若用户已离开，不抢回焦点。重试再次失败时保留错误状态，不自动循环；后续新尝试只能由用户再次明确点击触发。若模块代码本身执行/解析失败而无法安全重试，保留可理解的错误状态，不得伪报恢复成功。
- 实现前用网络故障注入验证三条路径：①后台预载失败 → 用户首次进入编辑自动触发一次按需加载并成功，不显示错误且无需第二次操作；②用户在预载未完成时进入编辑 → 共用原 Promise，其失败显示错误，手动重试再失败后错误仍在且不自动循环；③跳过预载进入编辑，首次按需加载失败 → 明确点击手动重试成功，错误清除并恢复编辑。三条路径都按 §3.3 统一计数口径断言加载尝试数、Promise/错误边界状态、错误清除与焦点恢复。

### 3.5 观测边界

- 预载效果通过本地浏览器测试或开发期性能读数验证，不增加生产遥测。
- 至少记录「用户主动打开编辑器」到真实 `EditorView` 首个可编辑帧的时长，并区分预载命中、预载仍在途、跳过预载、加载失败四种情形；门槛与计时端点以第 5 节为准。


## 四、实现边界与风险

### 4.1 延续现有编辑器底座

- 首轮实现范围限于现有即时渲染装饰与正文编辑器加载入口；不改数据模型、API、同步、保存策略、表格能力，不新增生产依赖或替换编辑器。
- 这些只是用户批准设计后的候选实现边界；本稿阶段不实施，也不修改既有定稿文件。

### 4.2 以语法范围驱动装饰（待议提案）

> 本小节的门槛改动与三份现行定稿冲突，见 §1.2 与 §4.6 第 6 条；未获用户批准不进入实现。其余小节（4.1、4.3 起）不受此限制。

- 将现有「活动行整行保留源码」门槛改为按语法节点与标记范围判定：完整节点即使处于活动行也可装饰；未完整识别的节点维持原文。
- 对折叠光标，使用 Markdown 源码半开区间 `[from, to)` 标识隐藏标记；命中标记时显现包含该标记的最小受支持语法节点，链接的方括号、圆括号和目标地址均映射到同一链接节点。嵌套语法优先显现最内层匹配节点；非折叠选择不触发源码显现。

- 只对当前视口与受影响的增量范围计算装饰。禁止为即时呈现改成每键同步解析整篇文档。

### 4.3 解析预算与装饰刷新

- **现状（v0.8.36，`apps/web/src/app/editor/live-preview.ts`）**：以 `const PARSE_BUDGET_MS = 50` 调 `ensureSyntaxTree(view.state, view.viewport.to, PARSE_BUDGET_MS) ?? syntaxTree(view.state)` 取视口语法树，未完成时回退到部分树；重建时机按即时渲染 v3（v0.6.5）定为「打字停手 90ms（`REBUILD_IDLE_MS = 90`）重算、`selectionSet`/`focusChanged` 走下一帧且同帧多次合并成一次」。**v4（v0.8.20）已修掉一个相关缺陷**：早期定时器重算只改插件自己的 decorations 字段、CodeMirror 只在下次 `update` 才重读，导致粘贴后永远停在源码；定稿记为「重算发生在 `update` 之外时**必须触发一次 update**」，实现是定时器回调里 `if (notify) view.dispatch();`。已核对仓库锁定的 `@codemirror/language@6.12.4`：`forceParsing` 有限时推进解析、返回是否到达目标，并在解析树引用变化时调用 `view.dispatch({})`。
- **因此本节的缺口不是「空事务不生效」**：v0.8.20 之后，插件**自身路径**（`update()` 与 90ms 定时器）里的空事务确实会触发重算。真正的缺口是——本稿设想的续解析链跑在插件**之外**，由自己的低优先级调度任务调 `forceParsing`，没有任何路径通知 `LivePreviewPlugin.update`，因而必须有一个显式、可判旧的信号把「现在可以重算了」送进去。`parseProgressEffect` 的作用是这个，**不是**绕过 v0.8.20 的缺陷。若实现阶段发现能让整条链从插件内部发起（从而无需外部 effect），优先采用更简单的方案，但必须重新验证停止条件与时延结论不变。
- 实现候选：每个 `EditorView` 至多一个续解析任务；每次在独立低优先级任务调用 `forceParsing(view, viewport.to, 5)`，5ms 是单次同步预算初始值，须由性能测试确认或调整。比较调用前后的解析树引用与 `syntaxTreeAvailable`；若解析树引用改变、首次覆盖目标视口或 `forceParsing` 返回 `true`，派发带 `{ generation, taskSeq, docVersion, viewportFrom, viewportTo }` 的 `parseProgressEffect`。其中 `generation` 在文档/视口/模式/视图生命周期变化时递增，`docVersion` 在 `docChanged` 时递增，`taskSeq` 对每个实际执行任务单调递增。`LivePreviewPlugin.update` 必须检查该 effect，仅当 generation、最新 taskSeq、docVersion、当前模式及目标视口范围全部匹配时重建装饰；过期 effect 被丢弃。effect 不改文档或撤销历史。回调在调用 `forceParsing` 前验证 token、仍处于即时渲染模式且 `view.composing === false`，调用后、派发 effect 前再次验证；过期回调不得调用 parser。若组合输入已开始，取消本轮调用、不派发 `parseProgressEffect`，只记录待刷新状态；待 `compositionend` 后基于最终文本建立新 generation 再续刷。`forceParsing` 是同步操作，不会被另一个浏览器任务插入；若其自身引发嵌套 ViewUpdate，仍须在外层返回后重验 token，避免旧任务派发。关于 `forceParsing` 自带的空事务与插件重算的关系，见本节第 1、2 条（**v0.8.20 已让插件自身路径的空事务生效，本节不需要为此再补 workaround**）；A12 仍须证明显式 effect 到 `ViewUpdate` 再到 DOM 装饰的完整链路。`forceParsing` 返回 `true` 只作为解析进展信号，不单独作为目标覆盖判断；是否覆盖视口目标只由 `syntaxTreeAvailable(view.state, parseTarget)` 判定。每次有效解析进展最多触发一次装饰重算。
- 视口覆盖使用唯一谓词：`parseTarget = view.viewport.to`（按 `view.viewport` 的半开结束偏移取目标），并以 `syntaxTreeAvailable(view.state, parseTarget)` 判断是否覆盖；不得用装饰范围或某个语法节点的 `to` 推断。`ViewUpdate` 中若 `docChanged`、`viewportChanged`，或由 `Editor` 的 mode setter 在 `Compartment` 重配置时显式通知模式变化任一发生，同一更新只递增一次 generation、取消旧句柄并清空停滞计数，随后更新 `docVersion`/视口端点；仅当仍处于即时渲染、未组合输入且谓词为 false 时才启动新链。视图销毁只递增 generation、取消并退休，不重排。仅由匹配的 `parseProgressEffect` 引起的更新刷新装饰，不创建新 generation。
- 续解析任务须在不同事件循环任务间让出执行：优先 `scheduler.postTask(..., { priority: "background" })`，不支持时用一个 `setTimeout(..., 0)` 任务；禁止 Promise microtask 自旋。每视图至多一个待执行任务，单次 `forceParsing` 预算候选 5ms。每个 taskSeq 在 `forceParsing` 前后按进展定义取样，文档/视口/模式/视图生命周期变化会使旧回调失效并重置计数。进展定义为 `forceParsing` 返回 `true`、解析树引用改变或 `syntaxTreeAvailable` 从 false 变 true。
- 每个 taskSeq 在 `forceParsing` 前后各取一次进展样本。第一次无进展时记录 `noProgressSince`，仍安排一个新的独立任务以便获得第二个样本；即使 `syntaxParserRunning` 在两次样本间从 true 变为 false，也不得跳过这次检查。若两个不同 taskSeq 均无进展且 `syntaxParserRunning(view) === false`，停止并记 A12 失败；若 parser 仍运行，则从 `noProgressSince` 起最多 2 秒，期间每次进展重置计时，届时 watchdog 安排一次新 taskSeq 检查；仍无进展即取消并记 A12 失败。目标视口覆盖时停止。离开「即时渲染」模式或销毁视图时，先取消全部待执行句柄、递增 generation 并清除停滞计数；处于其他模式期间不得续排。切回即时渲染时重新建立代次，只在当前视口仍未解析完整时创建新链；文档/视口变化同样使旧回调失效并重置计数。过期 generation 不得更新视图。
- 初始产品方向不加固定防抖。若同一更新的解析、装饰或 DOM 呈现仍导致可感知卡顿，先用性能读数定位具体阶段，再提出最小调整并重新验收。

### 4.4 IME、历史与编辑语义

- 中文输入法组合期间沿用现有保护：不重建装饰、不改焦点或选区；组合结束后对最终文档状态更新一次。
- 保持 CodeMirror 原生历史与快捷键语义；应用装饰、揭示语法标记、切换「仅编辑 / 即时渲染」不得丢内容或重置撤销栈。
- 鼠标点击、方向键、扩展选择、复制粘贴都以底层 Markdown 偏移为准；源语法标记的局部显现不能吞键、跳位或改变复制结果。

### 4.5 加载器与失败隔离

- 沿用 `apps/web/src/features/notes/ui/NoteWorkspace.tsx` 的动态导入，提取可由 React 懒加载和空闲预载共用的模块加载函数；保持代码分割，不静态并入首屏 bundle。
- 仅在用户主动进入编辑且模块尚未就绪时显示正文区占位；预载或编辑器加载故障不得遮住应用其它区域或修改正文。
- 错误恢复按 §3.4 清理被拒绝的共享 Promise、重置懒加载错误边界并确保单一重试；实施前必须用真实模块网络故障注入验证，且不能自动改变模式。

### 4.6 主要风险与控制

1. **隐藏标记的可达性与光标映射**：CodeMirror 原子范围可能让光标跳过被替换的语法字符，与「进入标记时局部显示源码」冲突。需在真 CM6 测试中验证点击、方向键和撤销，不可只测纯函数装饰结果。
2. **部分语法树导致更新悬空**：若解析已推进但没有触发视图更新，用户仍会观察到旧装饰。必须测试慢解析/长文档，并证明续刷有界且无需用户移光标。
3. **即时装饰造成输入卡顿**：活动行变成即时渲染后，每次编辑都会更新更多装饰；用短文和长文分别测解析、装饰、下一帧，不以平均数掩盖尖峰。
4. **IME 与选择/剪贴板回归**：现有保护需以真实 `EditorView` 和人工中文输入法验收；隐藏标记时复制仍须包含原 Markdown。
5. **预载竞态与故障重试**：预载尚未完成、被省略或 Promise 失败时，用户主动进入编辑都必须有明确且可恢复的路径，不能重复加载、无响应或丢焦点。
6. **与三份现行定稿冲突（本稿最大的一项，已按用户 2026-10-18 决定标为待议提案）**：本方案的门槛改动与 `wiki/Menote-项目架构-v1.md` §3.3、`docs/modules/Menote-即时渲染-设计-v1.md` §三、`docs/modules/Menote-编辑器专项优化-设计-v1.md` D1 三份**现行定稿**冲突（三者都定稿「光标所在行显示源码」，后者还定稿「即时渲染维持行内装饰路线」）。**本稿不修改它们，也不假定它们失效。** 用户若认可门槛改动，需另行确认是否授权回写这三份文件及其版本表；在此之前现行规则继续有效，本稿的 §2 与 §4.2 不得进入实现。§3 预载与 §4.3 解析续刷不涉及这三处，可独立推进。

### 4.7 开始实现前必须证明

## 五、验收标准

每项验收均按「用户动作 + 可观察结果」记录，并标注自动化、真实浏览器或人工输入法路径。**本节是未来实现的验收门槛，不代表本稿创建时已实施或验证通过。**

### 5.1 测量约定

- **预载命中激活路径**：在同一台 Windows 参考设备、同一 Chrome 稳定版、固定窗口尺寸与同一构建中，确认模块预载完成后重复 30 次打开编辑器；每轮从「仅预览」、且当前无挂载 `EditorView` 开始，模块代码保持已预载。该指标测组件激活/挂载，不测模块网络下载；预载仍在途、被跳过与冷加载路径另行报告，不套用此 p95 门槛。起点为进入编辑的激活事件；终点为首次 `requestAnimationFrame` 同时满足真实 `EditorView.dom.isConnected` 且 `contentDOM.contentEditable === "true"`。记录 p50/p95/失败次数；p50 用中位数（偶数样本取中间两值均值），p95 用 nearest-rank（升序后第 `ceil(0.95 × N)` 个样本），本节其它分布统计同法计算；p95 必须 **≤100ms**。另以独立焦点/输入检查确认，一次明确进入编辑的用户操作即可将焦点交给编辑器并键入，不需第二次点击。焦点恢复是行为验收，不把 `EditorView.hasFocus` 混入视图激活时延端点。报告 OS、CPU/内存、浏览器完整版本、视口尺寸与构建标识。
- **即时渲染端到端时延**：用固定的典型短文 Markdown 样本。起点为使目标语法首次完整的文档更新事务；终点为首个实际绘制出目标样式的浏览器帧。该时延 p95 必须 **≤100ms**；另外从解析树首次覆盖目标节点（`syntaxTreeAvailable`）计时，样式必须在下一帧呈现。不得添加固定防抖。两种时延都要记录，不能只测解析完成后的最后一帧。
- **短文样本**：使用以下固定内容作为测试源码中的多行常量，并以相同内容重复执行插入/撤销动作。
  ```markdown
  # 标题

  正文含 **粗体**、*斜体*、[链接](https://example.invalid) 与 ~~删除线~~。

  - 列表项一
  - 列表项二
  ```
**长文样本**：使用无随机数的固定生成器 `editor-fixture-v1`。下列模板按数组中的 **10 个单行字符串** 逐项列出；代码围栏开行、代码内容行、闭行分别是第 8、9、10 个模板项，不是一个含内嵌换行的单个模板。对每个物理行按模板顺序循环，`{i}` 替换为从 1 开始的十进制物理行号；行与行之间只用 LF (`\n`) 分隔，文档不加末尾换行。**图片一项固定用 `#pending`**：它仍是即时渲染 v6 认得的分支，但不发外部请求，换成真实地址会给性能基线引入与渲染无关的网络噪声（`.invalid` 域名必然解析失败，也会污染控制台与失败请求统计）。

````text
# 标题 {i}
段落含 **粗体**、*斜体*、~~删除线~~、`行内代码` 与 [链接](https://example.invalid)。
> 引用 {i}
- 无序列表项 {i}
1. 有序列表项 {i}
---
![图片](#pending)
```md
代码行 {i}
```
````

- **20,000 行样本**：精确生成 20,000 个单行模板字符串（`i = 1…20,000`，每个数组项不含 LF），用 19,999 个 LF 连接且不追加末尾换行。断言 `lines.length === 20_000`、`doc.split("\n").length === 20_000`、`!doc.endsWith("\n")`，并在装入 CodeMirror 后断言 `EditorState.doc.lines === 20_000`。代码围栏每 10 行重复：第 8 项开围栏、第 9 项代码、第 10 项闭围栏，第 11 项为下一组标题；前两组必须断言该边界顺序，围栏不跨组延续。
- **800 KB 样本**：目标严格为 **800,000 UTF-8 字节**（十进制，不是 800 KiB），使用固定生成器 `editor-fixture-v1` 与同一模板序列，从 `i=1` 开始逐行生成。每个模板项必须是单行字符串；用 `TextEncoder` 计算行 UTF-8 字节，文档仅以 LF 分隔且无末尾 LF。下一个模板行若超出目标，或加入后仅剩 1 字节（不足以再加 LF 与至少一个 `x`），该模板行不纳入文档，末行改为单独的 `x.repeat(padBytes)`；`padBytes` 只计 x 行本身字节，不含前置 LF。若模板行刚好填满目标，则保留该行、不添加填充行，`padBytes=0`、`paddingLineIndex=null`。记录生成器版本、`templateRowsWritten`、`firstExcludedTemplateIndex`（首个未写入模板的 1-based 索引，恒等于 `templateRowsWritten + 1`）、1-based `paddingLineIndex`（无填充时为 null）、`padBytes` 与字节账本。

参考伪代码（`targetBytes` 参数供边界单测使用；正式样本固定传 `800_000`）：
```js
function generateByteFixture(targetBytes = 800_000) {
  const encoder = new TextEncoder();
  const byteLength = (text) => encoder.encode(text).length;
  const lines = [];
  let byteTotal = 0;
  let i = 1;
  let templateRowsWritten = 0;
  let firstExcludedTemplateIndex = null;
  let paddingLineIndex = null;
  let padBytes = 0;

  assert(Number.isSafeInteger(targetBytes) && targetBytes >= 1);
  while (true) {
    const line = renderTemplate(i); // 固定十项循环，{i} 用十进制 i 替换
    assert(!line.includes("\n") && !line.includes("\r"), "template row must be one physical line");
    const separatorBytes = lines.length ? 1 : 0;
    const candidateBytes = byteTotal + separatorBytes + byteLength(line);

    if (candidateBytes === targetBytes) {
      lines.push(line);
      byteTotal = candidateBytes;
      templateRowsWritten += 1;
      i += 1;
      firstExcludedTemplateIndex = i;
      break;
    }

    // 超限或只剩 1 字节：不接纳候选模板行，另加独立 x 填充行。
    if (candidateBytes > targetBytes || targetBytes - candidateBytes === 1) {
      firstExcludedTemplateIndex = i;
      padBytes = targetBytes - byteTotal - separatorBytes;
      if (padBytes < 1) throw new Error("fixture padding invariant failed");
      paddingLineIndex = lines.length + 1;
      lines.push("x".repeat(padBytes));
      byteTotal += separatorBytes + padBytes;
      break;
    }

    // 此处 candidateBytes < targetBytes，且剩余至少 2 字节。
    lines.push(line);
    byteTotal = candidateBytes;
    templateRowsWritten += 1;
    i += 1;
  }

  const doc = lines.join("\n");
  const byteLedger = lines.reduce((sum, line) => sum + byteLength(line), 0)
    + Math.max(0, lines.length - 1); // 每个 LF 计 1 字节
  assert(byteTotal === byteLedger && byteLedger === targetBytes);
  assert(byteLength(doc) === targetBytes && !doc.endsWith("\n"));
  assert(firstExcludedTemplateIndex === templateRowsWritten + 1);
  if (padBytes > 0) {
    assert(paddingLineIndex === lines.length);
    assert(lines[lines.length - 1] === "x".repeat(padBytes));
    assert(lines.length === templateRowsWritten + 1);
  } else {
    assert(paddingLineIndex === null && lines.length === templateRowsWritten);
  }
  return {
    version: "editor-fixture-v1", doc, targetBytes, templateRowsWritten,
    firstExcludedTemplateIndex, paddingLineIndex, padBytes, byteLedger,
  };
}
```
边界单测对同一 `renderTemplate` 至少覆盖：`targetBytes=1`（仅一个 `x` 行）、精确命中首模板行字节数（无填充）、目标恰比接纳第二模板行后的累计字节数多 1 字节（第二模板行不纳入，末行为独立 `x` 行）、目标比接纳第二模板行后的累计字节数少 1 字节（超限分支），以及正式 `800_000` 样本。按上列十项模板，第 1 项渲染为 `# 标题 1`（10 字节）、第 2 项为 `段落含 **粗体**…`（105 字节），接纳第二项后累计 116 字节，故四条边界用例的目标字节分别是 `1`、`10`、`117`、`115`，期望 `padBytes` 分别是 `1`、`0`、`106`、`104`。每例均断言账本、`doc` 字节数、末尾无 LF、填充行独立性、`paddingLineIndex` 与首个未写模板索引；按上列十项模板、UTF-8 字节规则，正式 v1 样本还须断言 `templateRowsWritten=34_277`、`firstExcludedTemplateIndex=34_278`、`paddingLineIndex=34_278`、`padBytes=1`。这些元数据随 `editor-fixture-v1` 一起固定，任何变更须升样本版本。
- **长文性能**：分别在深滚动与中段编辑时记录解析、装饰、下一帧及主线程 `longtask`。
- **长任务判定**：使用 `PerformanceObserver` 的 `longtask`（≥50ms），沿用 `apps/web/src/features/editor-lab/perf.ts:7-48` 的动作起点（`LabAction`）和 800ms 归因窗口（`ATTRIBUTE_WINDOW_MS` / `attributeLongTask`）。先对现行实现、再对候选实现运行同一动作集；候选实现不得引入新的、可归因于渲染的长任务；若基线已有同类任务，候选的出现次数与最长时长不得恶化。另报告同机 p50/p95，不能只报告均值。
- 现行即时渲染文档记载 800KB headless 增量解析与局部装饰中位 **26ms**，它不是浏览器真实打字延迟，不能直接当成此次验收通过线；实现前须在同设备、同浏览器先建立现行实现基线。
- 性能读数留在本地测试或开发期，不新增生产遥测。异常样本、浏览器版本、机器信息和网络模拟条件都要记录。

| A12 | 触发解析预算未覆盖视口的路径并保持光标不动；在续解析已排队后分别改文档、滚动视口、切换模式或销毁视图 | 每视图至多一个待执行续解析；每次 `forceParsing` 预算以 5ms 为初始候选（如基准测试要求变更，实施前先更新并确认门槛）。每次调用前后按 `taskSeq` 取样；解析推进时带完整 token 的 `parseProgressEffect` 必须使装饰刷新一次。状态变更后的旧回调不得调用 `forceParsing`，旧 effect 必须被丢弃、不更新装饰。无进展后仍执行下一独立任务取第二样本；即使 parser 在两样本间由运行变停止也不能跳过。两任务均无进展且 parser 已停时停止并判失败；parser 仍运行但 2 秒无进展时 watchdog 安排独立复查，仍无进展即失败；任何进展重置计时。视图销毁/模式变化/范围覆盖时取消；不得忙循环或依赖用户输入/移光标/失焦 | 真 `EditorView` 定向自动化 + 可注入延迟解析器/状态切换 + 模拟时钟 + `ViewUpdate`/effect 探针 + 长文性能测试 |
