MeNote · 横向滚动条样式 · 方案对比

四个方案放在同一页、同一套真实场景里横向对比。每个演示块都是能真滚的——用滚轮横向 / 触控板 / Shift+滚轮 / 拖动把手 / 点边缘按钮都行，鼠标移出后会看到各方案在"静止态"的差别。 令牌与 apps/web/src/app/theme/tokens.css 一致，尺寸照抄实现（表格行高 34px、列最小 96px、 属性行固定 26px），所以这几块看着就是现在 App 里的样子，不是美化过的插画。

文档：评审稿（不是实现） 依据：DESIGN.md v1.12 §2.7 滚动归属 / §3.2 颜色令牌 / §2.2 结构尺寸 日期：2026-10-04
深浅两套都要看：滑块对比度是这次的关键，浅色下最容易暴露"灰条发脏"。

先说结论

查出来的两处真问题（四个方案都会顺手修掉）

  1. 正文代码块没带细滚动条类违和主因
    app.css:1071 的 .markdown-body pre 只有 overflow-x: auto， 全仓库 11 个滚动条相关文件里唯独它没挂 .scroll-thin。结果：表格是 8px 细条、 代码块是 Windows 默认那根 15–17px 的粗条（灰轨道 + 深色滑块 + 边框）， 同一屏里两种滚动条并存——这就是"违和"最刺眼的一处。
  2. 属性行把条完全隐藏，截断后没有任何提示不是丑，是看不见
    app.css:4608 的 .addentry__extras 写着 scrollbar-width: none + ::-webkit-scrollbar { height: 0 }。DESIGN.md §2.2 已定「字段行固定 26px、不换行、 越界横向滚动」，所以这里不能加会撑高的条；但"越界了"这件事对用户完全不可见。 四个方案在这处统一改为：保持 0 占位 + 加边缘渐隐提示。
  3. 四处横向滚动的口径现在不统一：表格 .tablegrid__scroll（带细条）、 代码块 .markdown-body pre（无样式）、版本对比 .versiondiff__scroll （带细条但和表格同一套）、属性行 .addentry__extras（隐藏）。 无论选哪个方案，第一步都是把它们收进同一个共享类，否则下次加新屏又会各写各的。

方案 0 · 现状（基线）

不改任何东西，作为对照。请重点看代码块那块：它是系统默认粗条，与旁边表格的细条并排出现； 属性行则完全没有提示，只看得出内容被切断了。

  • 常驻占位 8px（代码块 15–17px）
  • 不需要 JS
  • 改动面：无

方案 A · 统一细轴（最小改动）

把所有横向滚动处收进一个共享类，轴从 8px 收到 6px、滑块可见粗细 2px。 完全不动布局、不加 JS、不加标记——只是"全都变成同一根细条"。 这是最不容易出事的方案：视觉变化小，但"违和"和"代码块太粗"两个问题当场消失。

  • 常驻占位 6px
  • 不需要 JS
  • 改动面：app.css 一处规则 + 4 处挂类

CSS（进 app.css，组件只挂类名）

/* 横向滚动统一口径：表格网格 / 正文代码块 / 版本对比 / 属性行 */
.hscroll {
  scrollbar-width: thin;
  scrollbar-color: var(--line-2) transparent;
}
.hscroll::-webkit-scrollbar { width: 8px; height: 6px; background: transparent; }
.hscroll::-webkit-scrollbar-thumb {
  border: 2px solid transparent;          /* 配合 content-box → 可见 2px */
  border-radius: var(--radius-pill);
  background: var(--line-2);
  background-clip: content-box;
}
.hscroll::-webkit-scrollbar-thumb:hover {
  background: var(--muted);
  background-clip: content-box;
}
.hscroll::-webkit-scrollbar-corner { background: transparent; }

/* 属性行：DESIGN §2.2 固定 26px 不换行 → 不给条，改为边缘渐隐 */
.addentry__extras { scrollbar-width: none; }
.addentry__extras::-webkit-scrollbar { height: 0; }

代价与风险

  • 静止时那条线一直在——表格底部永远少 6px 高的可视区，"占太多空间"只缓解 2px。
  • 滑块对比度低（--line-2 压在 --bg 上 ≈ 1.6:1）：够克制，但也够难找。
  • 不动 JS = 键盘聚焦时不会有额外提示（轴本来就在，可接受）。
  • 需给代码块、版本对比两处补挂类；属性行的"截断无提示"只能靠渐隐补，不是这条规则能解决的。

方案 B · 细轴 + 悬停 / 滚动淡入（建议）

规则与 A 相同（同一份 CSS），只是滑块静止时是透明的：鼠标移进容器、或正在滚动、或键盘焦点进入时淡入， 停手约 0.9s 后淡出。轴的位置仍然留着 6px，所以不会出现"一滚动页面高度就跳一下"。 静止时那一行是干净的，而"能横滚"这件事在鼠标移入的瞬间就交代清楚。

  • 常驻占位 6px（静止不可见）
  • 需要 1 个 hook（约 15 行）
  • 改动面：app.css 一处规则 + 1 个新文件 + 4 处挂类

CSS + hook

/* 与 A 同一条规则，只是滑块静止透明 */
.hscroll {
  scrollbar-width: thin;
  scrollbar-color: transparent transparent;   /* Firefox：起手透明 */
}
.hscroll::-webkit-scrollbar { width: 8px; height: 6px; background: transparent; }
.hscroll::-webkit-scrollbar-thumb {
  border: 2px solid transparent;
  border-radius: var(--radius-pill);
  background: transparent;                    /* 静止：不画 */
  background-clip: content-box;
}
.hscroll:hover,
.hscroll.is-scrolling,
.hscroll:focus-within { scrollbar-color: var(--line-2) transparent; }
.hscroll:hover::-webkit-scrollbar-thumb,
.hscroll.is-scrolling::-webkit-scrollbar-thumb,
.hscroll:focus-within::-webkit-scrollbar-thumb {
  background: var(--line-2);
  background-clip: content-box;
}
.hscroll:hover::-webkit-scrollbar-thumb:hover { background: var(--muted); }
.hscroll::-webkit-scrollbar-corner { background: transparent; }

/* app/dom/hscroll-reveal.ts —— 一个 hook，四处复用 */
export function hScrollReveal(el: T): T {
  let t: ReturnType | undefined;
  const show = (ms: number) => {
    el.classList.add("is-scrolling");
    clearTimeout(t);
    t = setTimeout(() => el.classList.remove("is-scrolling"), ms);
  };
  el.addEventListener("scroll", () => show(900), { passive: true });
  el.addEventListener("focusin", () => show(1600));   // 键盘可达也要看见
  return el;
}

代价与风险

  • 空间上只比 A 少「静止时那 2px 细线」——如果你的不满主要是"占高度"，B 和 A 一样要占 6px。
  • 静止时看不见滑块 = 可发现性略降；靠"鼠标移入即现"兜住，触屏本来就没有条（触摸拖拽直给）。
  • 需要一个 15 行 hook；prefers-reduced-motion 下淡入会变瞬时（全局已有该规则），可接受。
  • Firefox 走 scrollbar-color：渐隐没有过渡，是硬切换；Chrome/Edge 无此问题。

方案 C · 零占位悬浮把手 + 边缘渐隐

原生条彻底隐藏，不占任何高度：鼠标移入或滚动时，内容上浮出一条细把手（可拖）， 左右边缘按"那边还有内容"淡入渐隐，极窄的容器（代码块、属性行）只给渐隐、不给把手，避免压住字。 空间账是四个方案里最干净的，代价是把滚动条变成了自绘控件。

  • 常驻占位 0px
  • 需要复用控制器（约 70 行）
  • 改动面：共享类 + 控制器 + 4 处接入 + 键盘可达

CSS + 控制器要点

.hscroll { scrollbar-width: none; }
.hscroll::-webkit-scrollbar { display: none; width: 0; height: 0; }

.hs { position: relative; }
.hs__fade {                            /* 边缘渐隐：只在悬停/滚动中出现，且只亮还有内容的那一侧 */
  position: absolute; top: 0; bottom: 0; z-index: 2; width: 30px;
  pointer-events: none; opacity: 0; transition: opacity .18s ease;
}
.hs__fade { width: 30px; pointer-events: none; }
.hs__fade--l { left: 0;  background: linear-gradient(90deg,  var(--bg) 35%, transparent); }
.hs__fade--r { right: 0; background: linear-gradient(270deg, var(--bg) 35%, transparent); }
.hs__handle {                         /* 悬浮把手：压在内容上，不占布局 */
  position: absolute; left: 0; bottom: 6px; height: 5px; z-index: 3;
  border-radius: var(--radius-pill); background: var(--line-2);
  opacity: 0; cursor: grab;
}
.hs:hover .hs__fade, .hs.is-scrolling .hs__fade,
.hs:hover .hs__handle, .hs.is-scrolling .hs__handle { opacity: 1; }
/* ↑ 但只在「那边真的还有内容」时才亮：JS 按 scrollLeft 打 .has-l / .has-r / .has-over
 *   渐隐不能常驻 —— 常驻会永久盖住首列前 30px（版本对比里那正是 +/- 符号的位置） */

/* app/dom/hscroll-overlay.ts（要点，非完整实现）
 *  - 把手宽度  = max(28, clientWidth * clientWidth / scrollWidth)
 *  - 把手位移  = (clientWidth - 把手宽) * scrollLeft / (scrollWidth - clientWidth)
 *  - 拖动      = pointerdown 记偏移 → pointermove 改 scrollLeft（pointer capture）
 *  - 键盘      = 容器 tabindex="0" + ArrowLeft/Right/Home/End（必须，DESIGN §6.1）
 *  - 无障碍    = 把手带 role="slider" + aria-valuenow/valuemin/valuemax
 *  - 窄容器（宽 < 240px）不挂把手，只给渐隐
 */

代价与风险

  • 自绘控件：把手要自己算比例、拖拽、键盘、role="slider"，测试面比 B 大一个量级。
  • 把手压在内容上（表格最后一行会短暂被压住），所以只在悬停/滚动时出现，不是常驻。
  • 静止态没有条也没有渐隐，"还有内容"只靠内容被裁切本身来暗示；没有悬停的场合（触屏）提示最弱，而 DESIGN §6.1 又要求不以悬停为唯一入口 → 真要做，得再补一个可点的翻页出口。
  • 容器高度很小时（属性行 26px）把手几乎贴边，实际只宜用渐隐。

方案 D · 表格专属「列导航条」，其它处走 A

表格是横滚的重灾区（列多就滚），所以给它一条有信息量的横条：不额外占一行， 并进表格底部既有的状态行（.tablesizebar 那一行），左边写「第 3–7 列 / 共 12」， 右边一条按列分的刻度，窗口块可点可拖。其它三处（代码块、版本对比、属性行）走 A 的统一细轴。

  • 表格占位 0px（并进既有行）
  • 表格专用（约 50 行）
  • 改动面：表格屏专属 + 其它处走 A

结构与要点

<!-- 表格屏：横条并进既有状态行，不新增块（DESIGN §2.1 块顺序不变） -->
<div class="tablesizebar">
  <div class="tablesizebar__foot">
    <span class="tablesizebar__count">128 行 · 12 列</span>
    <span class="size-tag size-tag--soft">412 KB</span>
  </div>
  <div class="tablesizebar__nav">              <!-- 新增：列导航条 -->
    <span class="navstrip__info">第 3–7 列 / 共 12</span>
    <div class="navstrip__track">              <!-- 点击/拖动 = 横向滚动 -->
      <div class="navstrip__ticks"></div>      <!-- 刻度按列宽分段 -->
      <div class="navstrip__win"></div>        <!-- 当前可见区间 -->
    </div>
  </div>
</div>

/* 要点：
 *  1. 刻度分段来自**已知的列宽**（表格列定义里有），不是均分 —— 所以刻度是诚实的
 *  2. 「实时计数必须可见」（DESIGN §5.4-2）本来就要求这一行有数字，列区间与它同族，不违和
 *  3. 图册视图没有列，不挂这条（避免「两视图行为不一致」）
 *  4. 其它三处仍走 .hscroll（A 的细轴），别把列导航条做成通用滚动条
 */

代价与风险

  • 最重的一个：表格是虚拟滚动 + 列宽可拖的组合，刻度窗口要跟着列宽变化实时重算。
  • 把"滚动条"和"状态/计数行"合并成同一块，这一行的信息密度会上升（要重排，不是加个条）。
  • 网格与图册两种视图行为不同（图表没有列），需要明确"图册不显示"的规则，否则会被当成不一致。
  • 代码块那处仍然只是 A 的细轴 → "违和"修掉了，但"占空间"只在表格这一屏解决。

三个需要你拍板的问题

  1. 你说的"占太多空间"，指的是高度还是视觉噪音？
    高度 → 只有 C（和 D 的表格部分）能把常驻占位降到 0，B 与 A 都还是 6px。 噪音 → B 就够了，且代价最小。选之前最好先明确这一条，因为四个方案的分歧点就在这。
  2. 代码块要不要"永远看得见"那根条？
    代码块是读长行的地方，滚到一半很容易忘记右边还有内容。四个方案里我给代码块的建议是 保留细轴（A/B 的做法），把 C 的悬浮把手留给表格这类容器。如果你想全站零占位，这处要单独拍。
  3. 属性行的"截断无提示"按哪种算修好？
    DESIGN §2.2 已定它固定 26px、不换行，所以任何会撑高的条都不行。我的默认做法是 0 占位 + 边缘渐隐（四个方案都这么做）。如果你觉得不够，可选：悬停时末项再渐隐一点、 或加一个可点的「›」翻页。

我的建议

选 B。它一次解决你说的两件事：违和——所有横向滚动处收进一个共享类， 代码块那根系统粗条被替掉；占空间——静止时那 6px 完全看不见，鼠标一移进去就交代清楚， 而且因为轴的位置留着，不会出现滚动时内容高度跳一下。

C 留作第二步。如果做完 B 你还觉得表格底部那 6px 是浪费，再把表格一处升级成 C 的零占位悬浮把手 （表格是唯一值得为它自绘的容器）。D 我不建议现在做：它最重，而收益集中在表格一屏， 等真用起来觉得"想知道现在看到第几列"再单独提。

无论选哪个，这三件事都要做（四个方案都含）：① 建共享类收口四处横向滚动； ② 给代码块补挂类（现在漏了）；③ 属性行加边缘渐隐，保持 26px 不变。
